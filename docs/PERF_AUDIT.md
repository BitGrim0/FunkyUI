# Аудит производительности FunkyUI vs Dear ImGui 1.92.9

Основа: результаты бенчмарка (Ryzen 7 3700X, RTX 3060 Ti, 100 Гц, Windows 11), чтение кода и A/B-стенды в wine и callgrind.
Стенды используют фейковые метрики глифов, поэтому их результаты даны как отношения к HEAD. Миллисекунды для вашей машины пересчитаны из этих отношений.
Если цифра получена моделью, а не измерена, это указано.

## 1. Короткий итог

Подтверждено **14 проблем**: 4 × P1, 2 × P2, 8 × P3. Из известного списка:
- K1, K4, K5, K6 и K7 подтверждены. Для K1/K4, K5 и K6 найдены решения лучше исходных подсказок.
- **K2 и K3 устарели.** Для ASCII уже есть прямой массив `SimpleIndex`, кернинг хранится таблицей строк int16. Хеша там нет.
- В K5 основная стоимость не хеш: это 6 вызовов `Pow` на каждый цветовой переход в каждом кадре.

Новые находки, которых не было в K1–K7:
- хеширование кадра в overlay-режиме, 10–20 % build в Display;
- лишняя работа с цветами у переходов, которые уже завершились;
- перевод `GlyphEntry` из формата хранения на каждом глифе;
- O(shapes×texts) в батчере;
- GC полным проходом в каждом кадре;
- две методологические ошибки бенчмарка: переходы не успевают завершиться в Throughput, и «GPU ms» включает простой GPU.

Ожидаемый эффект после всей волны. Эффекты не складываются линейно, поэтому даны диапазоны:

## 3. Разделы по проблемам

### P1-1. K1 + K4: двойная раскладка и три прохода по квадам текста (известная, решение лучше подсказки)

**Сейчас.**
- K1. `Controls.cpp:108→122`, `128→169`, `176→239`, `Ui.cpp:786→831` (заголовок панели) и `ToggleSwitch` в FunkyBench (`Main.cpp:177→194`) сначала вызывают `MeasureText`, потом `DrawString`. Каждый из вызовов проходит `LayoutSimple` целиком (`Text.cpp:1248-1264`), и каждый раз это 3 `HashCombine` плюс поиск в FrameCache.
- K4 и ещё два прохода, которых нет в K4. `Text.cpp:1236-1241` копирует 32-байтные `GlyphQuad` в `FrameLayouts`. `Draw.cpp:336-342` проходит по ним второй раз, чтобы собрать объединение границ. `Draw.cpp:354-372` проходит третий раз: пересобирает `Rect[2]/[3]`, а float-тексели снова переводит в int через `+0.5` и усечение. Во float их перед этим перевёл `PlaceGlyph` (`Text.cpp:201-208`) из uint16.
- A/B-стенд (1200 парных кадров) показал, что само удаление memcpy даёт около 2 %. Основная стоимость в проходах и конвертациях. Без текста build Menu = 0.59 от HEAD, то есть текст занимает около 41 % build Menu.

**Решение** (три шага, в этом порядке):
1. **Компактная запись.** `GlyphQuad` делается равным первым 24 байтам `GpuGlyph`: `float Rect[4]` относительно начала раскладки плюс `Texel0/Texel1`, упакованные прямо из uint16 `GlyphEntry`. `TextLayout` получает `Ink` (ClipRect), который накапливается в цикле `LayoutSimple`. Проход для границ убирается. Копирование сводится к «rect + origin, 2 копии текселей, цвет и clip вынесены из цикла». Градиент считается отдельным проходом только для градиентной кисти, и там же пара `From/To` переводится в линейное пространство один раз на строку, а не через `Lerp(Color)` на каждом глифе.
2. **Слитный путь для одноразового текста.** Для однотонной кисти `DrawString` резервирует хвост `ReserveGlyphs(text.size())`, `LayoutSimple` пишет туда готовые `GpuGlyph`, затем `CommitGlyphs(count, ink)`. Цвет берётся из `MakePaint().Fill0`, так выход остаётся бит-в-бит. Сложный (shaped) текст, градиент и будущие эффекты идут через Layout с копированием.
3. **K1 через публичный `FormattedText`** в стиле WPF/Avalonia: `FormattedText FormatText(text, style)` возвращает `{ Vec2 Size; float Baseline; const TextLayout* Layout; }`, а `DrawText(position, const FormattedText&, const TextStyle& paint)` рисует его. Label, Button, CheckBox, заголовок панели и ToggleSwitch в бенче переводятся на эту пару. `MeasureText`/`DrawString` остаются. В debug в структуре хранится `FrameIndex`, и `DrawText` его проверяет.

**Альтернативы.**
- Только компактная запись: 0.87 против 0.71 у слитного пути в текстовых сценах, то есть вдвое меньше.
- Скрытый memo «measure → draw»: нужен хеш строки или сравнение указателей (ARCHITECTURE запрещает хешировать строки), появляется скрытая связь, и собственным контролам через публичный API это недоступно.
- Кэш простого текста между кадрами по строке: ничего не даёт TextDynamic и противоречит архитектуре.
- `TextRun` из подсказки: после шага 1 это тот же дизайн, отдельный тип не нужен.

**Выигрыш** (A/B-стенд, p50 build относительно HEAD). Слитный путь: TextStatic 0.71, TextDynamic 0.72, TextFonts 0.72, Menu 0.92. K1 поверх компактной записи: Menu 0.87. Всё вместе: Menu ≈0.83. ImGui на том же стенде: 0.64 / 0.63 / 0.62 / 0.72.
На вашей машине (throughput build): TextStatic 0.546 → ~0.39 мс, TextDynamic 0.711 → ~0.51, TextFonts 0.376 → ~0.27, Menu 0.309 → ~0.26.
**Код:** примерно +80/−60 строк. Затронуты Internal.h, Text.cpp, Draw.cpp, Ui.cpp (разделение Reserve/Commit), Controls.cpp, FunkyUI.h (+10) и бенч.
**Чем платим:**
- TextSystem пишет формат `GpuGlyph` рендерера.
- Одноразовый путь резервирует `text.size()` инстансов с запасом, как `PrimReserve` в ImGui.
- `FormattedText` висячий после EndFrame; debug-assert это ловит.
- `DrawText` игнорирует шрифтовые поля paint-стиля, это нужно задокументировать.
- `TextLayout` становится на 16 Б больше.
- Уверенность высокая для отношений и средняя для абсолютных мс, потому что стенд использует фейковые метрики и настоящие строки кернинга Segoe UI отличаются.

### P1-2. Хеш кадра на каждой эмиссии в overlay-режиме (новое)

**Сейчас.** `EmitShapes` (`Ui.cpp:628`) и `EmitGlyphs` (`Ui.cpp:642`) перед каждой эмиссией вызывают `FoldEmitted` (`Ui.cpp:657-669`), а та делает 4 вызова `FrameHash::Fold`, по 2 imul на каждые 8 Б (`HashRound`, `Ui.cpp:249-254`). В Menu это около 7 400 вызовов за кадр, 3 716 из них с нулевой длиной. EndFrame дохеширует батчи и счётчики (`Ui.cpp:452-462`). В embedded-режиме функция сразу возвращается, поэтому стоимость видна только в Display.
Ваши цифры: build в Display больше, чем в Throughput, на +18 % в Menu, +20 % в TextStatic, +21 % в Idle, +35 % в Mixed, +47 % в Background и +55 % в Effects, и разница растёт с объёмом эмитированных байт. У ImGui та же разница +7…13 %, это холодный кэш после сна по vsync. По callgrind и парным циклам хеш занимает 10–20 % build в overlay.

**Решение: точное сравнение с прошлым кадром вместо хеша.**
- В overlay хранятся `Prev`-массивы для Shapes, Glyphs, Points, Clips и Batches. `BeginFrame` меняет местами заголовки `Array` (Data/Count/Capacity) с `Prev` до `Clear()`, так что ничего не копируется.
- `EndFrame` один раз сравнивает viewport/scale, 4 счётчика, Batches, Clips, Points, Shapes и Glyphs. Цикл идёт по uint64 через XOR/OR (или SSE2 cmpeq/movemask) с выходом на первом отличии. Текущий побайтовый `MemEqual` для этого слишком медленный.
- Present пропускается, если всё совпало и `!ForceRedraw`.
- **Инвариант:** любой EndFrame без Present ставит `ForceRedraw` (`!IsVisible()`, неудачный Render). Для обновления атласа и восстановления устройства это уже так.
- Удаляются `FrameHash`, `HashRound`, `FoldEmitted`, 4 счётчика `Hashed*`, `LastFrameHash` и ограничение на порядок в `EmitPolyline`. Раздел про пропуск кадра в ARCHITECTURE.md обновляется.

**Альтернативы.**
- Сравнивать на каждой эмиссии, пока данные в кэше: около 60 % стоимости хеша в Menu уходит на накладные расходы вызова, а они останутся.
- Хешировать один раз в EndFrame: измерено всего −3 %, байты те же, только холодные.
- Более быстрый хеш (wyhash, XXH3, CRC32C): не больше 2/3 выигрыша, стоимость по-прежнему пропорциональна байтам, CRC32C требует SSE4.2, коллизии возможны.
- Выбранный вариант точен. На меняющемся кадре выход происходит в первом КБ. На статичном кадре читается около 290 КБ (Idle), это примерно 5–10 мкс, и всё равно дешевле сегодняшнего хеша. В сумме строк становится меньше.

**Выигрыш** (только Display). Menu build 0.365 → ~0.31–0.335. TextStatic −0.07…0.11 мс, TextDynamic −0.08…0.12, TextFonts −0.04…0.07, Mixed −0.08…0.12, Background −0.13…0.175, Idle −0.03…0.06: CPU Idle 0.422 → 0.36–0.39, что равно или лучше ImGui (0.408). На стенде Ir в overlay после правки совпал с embedded, решения о present/skip те же.
**Код:** примерно −75/+45, в сумме около −30 строк.
**Чем платим:**
- В overlay появляется вторая ёмкость буферов: Menu +0.3 МБ, TextStatic +1 МБ, Background +1.1 МБ.
- Статичный кадр читает обе копии, это 2–3 % build.
- Появляются два инварианта: ForceRedraw ставится везде, где нет Present, и массивы не меняются после EndFrame.
- Паддинги должны быть детерминированы: `GpuShape` обнуляется, `GpuGlyph` пишется целиком. Хеш требовал того же.

### P1-3. Цветовые переходы (K5: хеш здесь не главное, решение лучше подсказки)

**Сейчас.**
- `AnimateValue(Color)` (`Ui.cpp:124-133`) в каждом вызове делает `ToLinear(target)` и `FromLinear(...)` (`Base.cpp:254-260`), это 6 вызовов `Pow` (Log2 с делением и Exp2), и никак не проверяет, завершился ли переход.
- `Animate` (`Ui.cpp:73-108`) всегда выполняет `MemEqual` (побайтовый цикл, `Base.h:44`) и `MemCopy` с размером во время выполнения и пересчитывает easing даже при `Elapsed == Duration`.
- На каждый Button и CheckBox приходится 2 цветовых перехода (`Controls.cpp:60-67, 149, 203`). В Menu это **2 808 `Pow` за кадр**.
- Оба стенда показывают: конвертации занимают 8.6–14 % build Menu, а поиск в хеш-таблице (сам K5) только 1–3.5 %.
- Попутно два бага. Новый переход крутит невидимую анимацию From==To всю свою длительность. Если после завершения перехода увеличить Duration, значение прыгает назад.

**Решение.** `TransitionState { float From[4], To[4]; float Progress; uint32_t LastFrame; uint64_t Target; }` занимает 48 Б вместо 60, слот таблицы 56 вместо 72 Б. `Target` хранит сырые биты цели: float, Vec2 или `PackColor`. Все три перегрузки идут через один помощник:
- новая запись создаётся с `Progress=1`;
- если биты цели не изменились и `Progress>=1`, обновляется `LastFrame` и цель возвращается как есть: ни конвертаций, ни арифметики, выход бит-в-бит;
- если цель изменилась: `From` = текущее значение, `To` = convert(target), это единственный `ToLinear`, `Progress=0`;
- `Progress += Dt/duration`, `FromLinear` вызывается только пока переход движется.

Копирования и сравнения фиксированы на 4 дорожки. Градиент в `DrawString` переводится в линейное пространство один раз на строку (входит в P1-1).

**Альтернативы.**
- Таблица `ToLinear` на 256 записей и пороговый поиск для `FromLinear`: ускоряет и движущиеся переходы, в Throughput Menu даёт около 91 % выигрыша от `Pow`. Но стоимость остаётся у каждого вызова, в том числе у покоящегося UI, это 2 КБ таблиц, а округление на границах меняется. Можно добавить позже, если Throughput Menu всё ещё будет важен.
- Быстрый путь только для цвета: остаётся 60-байтное состояние, остаются оба бага, не ускоряются float и Vec2 (сейчас 187 инструкций на вызов float, после правки 97).
- Интерполяция в sRGB: отвергнута, документация обещает линейное смешивание.

**Выигрыш.** Throughput Menu −10 % инструкций и −11 % циклов (build ~0.309 → ~0.275, CPU 0.362 → ~0.33). Idle −18 % циклов (build ~0.325 → ~0.27, это уровень ImGui). Display Menu build 0.365 → ~0.31. Mixed −0.02 мс. GPU и текстовые сцены не меняются.
**Код:** примерно +40/−45, без изменений API.
**Чем платим:** движущиеся переходы по-прежнему делают 3 `Pow` за кадр: 288 цветов CheckBox в Throughput Menu, около 31 % нынешних `Pow`. Поведение меняется только в двух багах, и оба при этом исправляются.

### P1-4. K6: тени панелей (известная, решение лучше подсказки)

**Сейчас.** Тень по умолчанию имеет offset (0,6) и blur 18, то есть σ=9 (`FunkyUI.h:387`). `EmitRoundRect` выпускает её отдельным инстансом с полями 3σ+aa = 28 DIP (`Draw.cpp:126-137`), это около 336×608 px на панель. На каждом пикселе выполняется полный путь SdRoundRect + Erf, потому что `SolidInterior` исключает `Softness > 0` (`Shape.hlsl:61`). Потом тело ещё раз закрашивает и смешивает около 156k тех же пикселей.
На 24 панели выходит около 5 Мпикс тени, из них 2.4 Мпикс насыщены под телом. Всего растеризуется около 9.6–9.9 Мпикс при цели 0.92 Мпикс. Обе библиотеки в Menu работают примерно на 40–45 Гпикс/с, то есть упираются в число пикселей и смешивание, а не в ALU.

**Решение: тень внутри инстанса тела** (для round rect со сплошной заливкой, это случай панели по умолчанию).
- Новый бит `FlagShadow` (биты 10–15 свободны). Смещение и σ кладутся в `P2.xyz` (без градиента P2 не используется), цвет тени в `Fill1`. Bounds = объединение охвата тела и тени.
- PS: `color *= Opacity; S = Premul(Fill1)*Opacity*(0.5-0.5*Erf(SdRoundRect(p-offset)*DpiScale/(σ√2))); return color + S*(1-color.a)`. Премультиплицированный over ассоциативен, поэтому результат равен двум нынешним смешиваниям, только с одним 8-битным округлением вместо двух.
- VS: быстрая область = внутренность тела ∩ прямоугольник тени, сжатый на `3.5σ + r·0.293 + 1/DpiScale`. Цвет в этой области считается один раз на инстанс.
- Тела с градиентом и тени без тела остаются на отдельном инстансе.
- Независимый двухстрочный первый шаг: пустить `Softness>0` в `SolidInterior` со сжатием 3.5σ. Ошибка Erf там 2.3e-4, это меньше собственной погрешности аппроксимации (5e-4).

**Альтернативы.**
- Только быстрый путь для размытой внутренности: убирает Erf, но все двойные смешивания остаются, это −5 %, если упираемся в смешивание.
- Полая тень из 4 полос: больше инстансов, и телу нужен второй прямоугольник.
- 9-slice текстура размытия (как в Skia): место в атласе на каждую пару (r, σ), новый тип инстанса, другая точность.
- Уменьшить тень по умолчанию: меняется внешний вид.

**Выигрыш.** Пикселей в Menu 10.5 → 6.8 Мпикс (−36 %), Erf-пикселей 5.6 → 3.2 Мпикс, на 264 инстанса меньше (−19 %, −25 КБ upload и сравнения). GPU throughput 0.222 → 0.13–0.15 мс, Display 1.18 → 0.7–0.8 мс. Пиксели посчитаны по геометрии, мс пересчитаны моделью.
FPS в Menu/Idle throughput не изменится, эти сцены ограничены CPU. Выигрыш достаётся игре, у которой мы забираем GPU: это главный сценарий overlay/embedded.
**Код:** примерно +40…60 (Draw.cpp 15–20, Shape.hlsl около 25, флаг).
**Чем платим:**
- два пути тени;
- пиксели кольца выполняют второй SdRoundRect + Erf (около +55 операций), небольшой риск по регистрам;
- возможен сдвиг на 1 LSB;
- мс надо подтвердить timestamps.

### P2-5. Размещение глифа из формата хранения (новое)

**Сейчас.**
- `GlyphEntry` хранит uint16 X/Y/W/H и int32 Left/Top (`Text.cpp:144-149`), и `PlaceGlyph` (`Text.cpp:201-208`) на каждом глифе переводит их в 8 float.
- Продвижение пера `x += float(adv+kern)*fontSize/unitsPerEm` (`Text.cpp:794, 824, 847`) выполняет настоящий `divss` на каждый глиф: без fast-math компилятор не заменит его умножением.
- `Round(x*dpi)` идёт через эмулированный `Floor` (`Base.h:352-354`), около 7 инструкций.

Это 33 000 глифов за кадр в TextStatic и 9 504 в Menu. У ImGui на глифе нет ни деления, ни конвертаций.

**Решение.**
1. `GlyphEntry` хранит `float Offset[4]` (пиксели от пера) и готовые `Texel0/Texel1`; `0xFFFFFFFF` означает «не разрешён». Заполняется один раз в `GetGlyph`/`AddToAtlas`.
2. `advanceScale = fontSize/upem` считается один раз на строку. Для upem = 2^k (Segoe UI, Arial, Consolas) результат точен бит-в-бит.
3. Снап пера делается как `float(int32_t(v+0.5f))` с `FK_ASSERT(v >= -0.5f)`. Это корректно, потому что простое перо начинается с 0 и движется только вправо.
4. Max считается как `min + width*dpp`, чтобы при дробном DPI выход был бит-в-бит.

**Альтернативы.** SSE внутри нынешнего `PlaceGlyph` не убирает сами конвертации и упаковку. Перо в фиксированной точке в единицах дизайна меняет суммирование, которое имитирует natural-режим DirectWrite. SSE4.1 `roundss` не входит в базовый SSE2.
**Выигрыш.** Build текста −8…14 % сам по себе и ещё около −10 % от снапа усечением. TextStatic −0.04…0.07 мс, TextDynamic −0.05…0.09, TextFonts −0.03…0.04, Menu −0.005…0.01. На символ выходит около 8–10 циклов против 13.3 сейчас и 7.8–8.2 у ImGui. Складывается с P1-1.
**Код:** ±15 строк в Text.cpp.
**Чем платим:** `GlyphEntry` 16 → 24 Б, SizedFont ~16 → 24 КБ. Для CFF со upem 1000 возможна разница ≤1 ulp на продвижение.

### P2-6. K7: медленный путь шейдера в Fill (известная, решение соответствует подсказке и уточнено)

**Сейчас.**
- `SolidInterior` (`Shape.hlsl:59-65`) сжимает фигуру на `r(1-1/√2)`. Для круга это вписанный квадрат, около 50 % квада, хотя точная внутренность занимает около 77 %.
- Медленный путь всегда распаковывает и смешивает обводку (`286-289`), даже при `StrokeWidth == 0`.
- Блок свечения с exp и делением (`293-299`), судя по DXBC, fxc делает безусловным.
- RoundRect стоит в `default` у switch.

Fill: 0.319 против 0.176 мс при сопоставимом числе пикселей, то есть упираемся в ALU медленного пути.

**Решение.**
1. `[branch]` на свечение. Обводка считается только при `StrokeWidth>0`. RoundRect проверяется до switch.
2. Точная быстрая область: VS выдаёт внутренний round rect (c, h, `ri = clamp(rmax-k, 0, min(h.x,h.y))`, `k = StrokeWidth + 1/DpiScale`). PS проверяет `max(q)<0 || dot(max(q,0),max(q,0)) < ri²`. Clamp по `min(h)` нужен, иначе область может стать неконсервативной.
3. `discard` на нулевой альфе не добавлять без GPU-захвата.

**Альтернативы.** Плоские фигуры из интерполянтов без загрузки буфера: около 9 интерполянтов и вторая копия покрытия. Геометрия-восьмиугольник: вдвое больше работы VS. Разбиение на квады внутренности и края: 5 инстансов на фигуру. Вариации PS по типу: ломают батчинг по порядку отрисовки.
**Выигрыш** (модель). Fill GPU −0.05…0.12 мс. Быстрая область 14.2 → 16.3 Мпикс/кадр (измерено). Background, Mixed и Ramp −несколько…15 % GPU.
**Код:** примерно +15/−5 HLSL, C++ не меняется.
**Чем платим:** +1 интерполянт; быстрая проверка длиннее на ~6 операций. Обязательно нужен замер на 3060 Ti, драйвер может снова развернуть ветки.

### P3-7. K3: кернинг (известная, формулировка устарела)

**Сейчас.** Хеша нет: `FontFace::Kerning[SimpleCount]` хранит строки int16 (`Text.cpp:169, 689-703`). Но на каждом глифе (`813-826`) есть загрузка `SimpleScripts` с 3-сторонней проверкой скрипта, `Kerning[previous]` с проверкой на null, `row[second]` и две проверки `KernUnknown/KernNeedsShaping`.
**Решение.** (a) держать строку предыдущего глифа в локальной переменной и обновлять её после ленивого выделения в `PairKerning`; (b) скрипты хранить битами (Common=0, Latin=1, Greek=2, Cyrillic=4) и проверять `m=s|run; (m&(m-1))==0`; (c) общая constexpr-строка `KernUnknown` добавляется только если замер после P1-1 покажет пользу.
**Альтернативы.** Плотная таблица ASCII 95×95: 18 КБ на шрифт, только для ASCII, выигрыш тот же. Кернинг только при `HasKerningPairs`: теряются шрифты только с GPOS. Убрать кернинг, как в ImGui: −22 %, но это видимая регрессия.
**Выигрыш:** −3…5 % build текста после P1-1 (−0.015…0.025 мс в TextStatic и TextDynamic). Уверенность средняя, потому что загрузки не зависят от x и OoO их скрывает.
**Код:** +10/−6. **Чем платим:** немного больше состояния в цикле.

### P3-8. K2: поиск глифа (известная, устарела) и MRU для SizedFont

**Сейчас.** Для ASCII глиф берётся как `sized.Glyphs[SimpleIndex(c)]` (`Text.cpp:830, 63-75`), это 2 сравнения. HashMap задействуется только для неразрешённых глифов и сложного текста. На каждую строку остаются 3 `HashCombine` (`1227/1254`, `500`) и `FrameCache::Find` (`219-234`).
**Решение.** Убрать K2 из плана. Добавить MRU на 1 запись (family, weight, italic, биты emPixels) → `SizedFont*` в общей точке входа Layout/Measure/EmitSimple, по образцу `LastBaked` в ImGui. Сбрасывать в `TextSystem::EndFrame` до освобождения Previous и в `ResetAtlas`.
**Альтернативы.** Memo на 4 записи: в сценах бенча лишних попаданий нет, строки сгруппированы по стилю. Передавать fontKey из Measure в Layout: это исчезнет вместе с P1-1. `SizedFont*` в `TextStyle`: засоряет публичную структуру props.
**Выигрыш:** 1–2 % (A/B: 0.985–0.994, в пределах разброса ±7 %). **Код:** +12. **Чем платим:** ещё один указатель, который надо инвалидировать.

### P3-9. O(shapes × texts) в батчере (новое)

**Сейчас.** `AddShapes` (`Ui.cpp:186-199`) вызывает `OverlapsText` (`Ui.cpp:220-229`) для каждой фигуры, и та проходит до 32 текстов уровня. Панель Menu накапливает около 20 текстов. BuildFrame занимает около 6 % кадра Menu, из них 50–61 % уходит на этот цикл.
**Решение.** Батчер хранит объединение границ глиф-ранов текущего уровня (расширяется в `AddGlyphs`, сбрасывается в `EndLevel`), и фигура сначала проверяется против него. Проверка консервативна, батчи остаются идентичны.
**Альтернативы.** Объединение фигур рана: −17 % против −50 %. Битовая сетка: на этой раскладке выигрыша нет. SIMD: та же O(n·m) и больше кода.
**Выигрыш:** BuildFrame примерно вдвое быстрее, Submit в Menu и Idle −0.01 мс (около трети разрыва 0.071 против 0.052). **Код:** +6. **Чем платим:** одна лишняя проверка для фигур, пересекающих объединение.

### P3-10. GC каждый кадр по всем слотам, таблицы не сжимаются (новое)

**Сейчас.** `CollectGarbage` (`Ui.cpp:276-291`) выполняется в каждом EndFrame, и `RemoveIf` (`Base.h:208-219`) обходит все слоты: Transitions 2 048 × 72 Б = 147 КБ, ContainerStates 128 × 312 Б = 40 КБ. Устаревшими записи становятся только через 8 кадров. `HashMap::Grow` (`Base.h:252`) только растёт, и после всплеска стоимость обхода остаётся на пике навсегда. Измерено 17.6k инструкций и около 1 150 промахов D1 за кадр.
**Решение.** Выполнять GC при `FrameIndex % MaxUnseenFrames == 0`. Обобщить `Grow` в `Rehash(capacity)` и сжимать таблицу при `Capacity>1024 && Count*8<Capacity`, по правилу FrameCache (`Text.cpp:271`). Разделять ContainerState не нужно.
**Альтернативы.** Инкрементальный GC (1/8 слотов за кадр): средняя стоимость та же, кода больше.
**Выигрыш:** −2…4 мкс на кадр (около 1 % в Menu/Idle), −165 КБ трафика, что немного помогает холодному кэшу в Display. **Код:** +12/−5. **Чем платим:** состояние живёт до 16 кадров; каждый 8-й кадр получает всплеск около 10 kcyc.

### P3-11. MemZero с размером во время выполнения в EmitShapes (новое)

**Сейчас.** `MemZero(shapes, sizeof(GpuShape)*count)` (`Ui.cpp:636`) превращается в вызов memset.
**Решение.** Обнулять по элементу: `shapes[i] = GpuShape{ .TypeFlags = CurrentClip << ShapeClipShift };`, тогда компилятор встраивает 96-байтные записи.
**Выигрыш:** −42k Ir на кадр, Menu −1.3 % build (−0.004 мс). **Код:** ±3. **Чем платим:** ничем.
Константный буфер на каждый батч (`Renderer.cpp:494-508`: 48 пар Map/Unmap в Menu, оценка 5–15 мкс Submit) откладывается, пока `FUNKY_PROFILE` не покажет, что он заметен. Если покажет, делать через `*SetConstantBuffers1` со смещениями и проверкой капы D3D11.1.

### P3-12. Бенчмарк: переходы в Throughput никогда не завершаются (новое)

**Сейчас.** `BenchCommon.h:919-921` переключает CheckBox каждые 40 кадров, Toggle каждые 90. Dt в FunkyUI берётся по настенному времени (`Ui.cpp:399-401`), длительности 90, 140 и 150 мс. При 2 625 FPS 40 кадров длятся около 15 мс, поэтому все 144 CheckBox и 24 Toggle анимируются постоянно: частичные галочки, свечение, конвертации. У ImGui других переходов нет.
Предложение «переключать раз в 400 кадров» не помогает: 400 кадров длятся около 150 мс, и переходы анимируются около 90 % времени.
**Решение.** Опциональный dt для embedded-режима в публичном API: хостам с игровым временем (пауза, slow-mo) он тоже нужен. В Throughput обе библиотеки получают номинальные 10 мс (`io.DeltaTime = 0.01` у ImGui). Строка «MenuFlat» (без теней и свечения) — по желанию.
**Альтернатива.** Пометить сцену как стресс-тест «всегда в анимации»: API не меняется, но сравнивается неравная работа.
**Эффект:** 0.02–0.025 мс CPU Menu/Mixed (5–8 %) и +5 % фигур окажутся артефактом. **Код:** около +10. **Чем платим:** новый параметр API; результаты несравнимы со старыми прогонами.

### P3-13. Бенчмарк: «GPU ms» включает простой GPU (новое)

**Сейчас.** `RunFrame` (`BenchCommon.h:1713-1714`) ставит начальный timestamp и очистку (`470-476`) до `Lib.EndFrame`, а тот сначала выполняет CPU-работу. По данным PDH время занятости = GPU % / Loop FPS:

| Сцена FunkyUI | Занятость PDH | Timestamps |
|---|---|---|
| Menu | 35.5 % / 2625 = 0.135 мс | 0.222 мс |
| TextStatic | 0.031 мс | 0.055 мс |
| TextDynamic | 0.129 мс | 0.321 мс |
| Fill (упирается в GPU) | 0.320 мс | 0.319 мс |

В сценах, ограниченных GPU, показатели совпадают, в остальных timestamps завышены.
**Решение.** Добавить колонку «GPU busy ms» в таблицу и CSV и помечать GPU ms как верхнюю оценку, когда CPU frame больше GPU ms. Для работы над шейдерами смотреть только Fill и Effects.
**Альтернатива.** Перенести очистку до timestamp: убирается только очистка, а не простой.
**Эффект:** только интерпретация. Разрыв в Menu по GPU составляет около 0.07 мс, а не 0.12, и в Throughput срочность K6 ниже. В Display на 100 Гц вопрос остаётся. **Код:** около +10.

### P3-14. Константы фигуры пересчитываются на каждом пикселе, квад дуги слишком велик (новое)

**Сейчас.**
- `FillColor` (`Shape.hlsl:219-231`) переводит концы градиента через pow на каждом пикселе, и это происходит даже на пикселях, где есть только свечение и покрытие равно 0 (`279-296`).
- `SdArc` (`122-141`) выполняет 2 sincos от углов фигуры на каждом пикселе.
- `DrawArc` (`Draw.cpp:236-237`) берёт bounds как квадрат полного круга.
- Путь Softness пересчитывает `Premultiply(Fill0)`, хотя VS уже выдаёт его в `input.Fill`.
**Решение** (по убыванию пользы на строку):
1. FillColor и тело считаются только при coverage>0.
2. Для дуги строится тесный bbox по экстремумам сектора. Пикселей дуг в Background 0.56 → 0.39 Мпикс.
3. VS считает линейные премультиплицированные концы градиента: +1 nointerpolation float4.
4. Путь Softness берёт `input.Fill`.
**Альтернатива.** Линейные концы градиента в `GpuShape` на CPU: +16 Б к каждому 96-байтному инстансу, а в VS они считаются бесплатно.
**Выигрыш** (модель): Effects GPU −10…20 % (0.391 → 0.32–0.35), Background и Mixed −2…5 %. **Код:** около +30/−10. **Чем платим:** +4 flat-скаляра; у дуги меняется смысл P1, если делать и этот пункт. Сцены и так выиграны, поэтому P3.

## 4. Отброшенные находки

- **Фиксированная стоимость BeginFrame / опрос Win32** (`Host.cpp:216-270`): меньше 10 мкс (Idle: 0.412 ≈ 0.325 + 0.088). Разрыв в Idle полностью объясняется сборкой панелей и Submit, так что делать здесь нечего.
- **Рост рабочего набора в Throughput из-за переименования динамических буферов при `WRITE_DISCARD`** (`Renderer.cpp:56-89`): механизм подтверждён (+53 МБ при 64 кадрах в полёте), но страдает только память и только в бенче. У хоста 1–3 копии (`SetMaximumFrameLatency(1)`), а у ImGui в той же сцене +240 МБ.
- **Потоковый upload / собственный memcpy**: бенч линкует CRT, выигрыш не измерен, memcpy — контракт клиента.
- **Константные буферы со смещениями D3D11.1**: отложено до профиля (см. P3-11).
- **Прямой массив для ASCII (K2 как сформулирована)**: уже сделано (`SimpleIndex`).
- **Хеш-таблица кернинга (K3 как сформулирована)**: уже таблица строк int16.
- **Разделение ContainerState на grid-only**: после P3-10 в замерах не видно, а в раскладку сетки добавятся лишние поиски.
